# 04_retour — enregistrer les notes du QR

One job : Page servie en local : un tap 1-4 par question → une ligne dans `revue` (ajout seul, inv. 3).

## Inputs
- Working : jeton du QR (aléatoire 128 bits) ou code court (8 caractères), tous deux stockés hachés par HMAC avec la clé locale `data/.cle-acces` (A1, #34) ; `brainiacs/<élève>/plans/AAAA-MM-JJ.md` (les questions à noter : le plan fait foi)
- Reference : `../../_config/retour.md` (écoute, port, adresse du QR) ; `../../_config/adviza.md` (port, empreintes des jetons de l'API ADVIZA)

Do NOT load : les `output/` d'autres runs, les autres étapes, `brainiacs/*/profil/`.

## Process (`python -m freinet.serveur`)
1. GET affiche, **seul POST écrit**, puis redirige. Défenses : clients hors réseau privé refusés ; en-tête Host limité au nom du QR, à `localhost` ou à une IP (DNS rebinding) ; Origin identique au Host (ou `Sec-Fetch-Site: same-origin`) exigé sur les POST ; corps borné ; 10 s par lecture et par requête, 32 connexions au plus dont 4 par client (lenteur volontaire) ; essais du code court limités par client (10 par 10 min) et en tout (60 : au-delà, la voie du code se ferme pour tous un moment, jamais celle du QR) — un attaquant du réseau local disposant de 8 adresses ou plus peut encore occuper les 32 places : accepté en V0, à la maison ; accès expirés au-delà de la fenêtre ; en-têtes stricts (CSP, pas de cache, référent limité à la page elle-même : le jeton est dans l'adresse, et `no-referrer` ferait envoyer `Origin: null`) ; journal sans l'adresse.
2. Une note par (plan, question) : identifiant dérivé des deux, donc un double tap n'ajoute rien ; une note différente = correction (événement compensatoire, `corrige_id`). `repondu_le` ramené au jour du ticket, `saisi_le` = maintenant. Un ticket se note de son jour à 7 jours après (ni avant, ni au-delà).
3. Joker « je sais déjà » (#26) sur la notion nouvelle → son premier rappel, le lendemain, est une question de transfert. Un joker seul compte comme un retour : le ticket est « noté ».
4. La page affiche l'objectif de la semaine : tickets notés sur 5 visés (#9), sans série à tenir.
5. Pages de lecture (A12) : `GET /cours`, `/cours/<carte>`, `/fiche/<concept>` servent la bibliothèque sans jeton, avec les mêmes défenses ; elles n'affichent aucune donnée d'élève et n'écrivent rien ; leur tête mène à la saisie du code (« Mon ticket »). Une source n'est un lien que si le registre de confiance l'admet (`freinet/pages.py`).
6. L'espace du ticket (PROF-11, `freinet/espace.py`) : tout ce qui suit `/r/<jeton>` ou `/k/<code>`, jeton vérifié à chaque page. Trois onglets : Aujourd'hui (notion du jour, chaque question avec « voir la réponse » et « revoir la leçon » en `<details>`, sans JavaScript ; après une note de 1 ou 2 l'`explication`, sinon le « Retiens » et un lien vers la fiche), Ma carte (l'état de chaque notion), Cours (la bibliothèque, liens préfixés par l'espace : on n'en sort jamais).
7. **API ADVIZA** (PROF-A, `freinet/api_adviza.py`) : même processus, second port, `127.0.0.1` seulement ; `Authorization: Bearer <jeton>`, un jeton = un élève (`_config/adviza.md`, empreintes SHA-256), jamais journalisé ; navigateurs refusés (`Origin`, `Sec-Fetch-Site`), Host de bouclage. Contrat `"1"`, JSON `no-store`, un GET n'écrit jamais. Lectures nommées (liste fermée) : `GET /adviza/etat` → `{contrat, releve_le, jauges{ticket{jour, statut, questions, notees, joker}, notion_du_jour, semaine{notes, objectif}, maitrise[{carte, nom, total, acquis, en_cours, debloque, verrouille}]}, a_faire[{id, titre, echeance}] (`ticket:<jour>` questions à noter, `notion:<jour>:<id>` « À découvrir : <titre> » quand le plan du jour a une notion nouvelle, `demain:<jour>:<id>` fiche à lire ; une entrée par jour et par notion, le jour même seulement), profil{nom, prenom, langue, fuseau, cartes[], concepts_acquis, concepts_en_cours}}` ; `/adviza/aujourdhui` → `{jour, langue, plan: null | {statut, joker, anecdote, revisions[{question_id, concept_id, concept, nature, enonce, reponse, explication, retiens, note}], nouvelle, demain, defi, avertissement}}` ; `/adviza/aujourdhui/<AAAA-MM-JJ>` (PROF-A4) → même forme, pour le plan de ce jour (jamais `plan: null`) : jour strict `[0-9]{4}-[0-9]{2}-[0-9]{2}` en fin de chemin (sinon 404 « lecture inconnue »), date réelle (404 « jour invalide »), dans la fenêtre du QR, du jour du ticket à 7 jours après (`retour.verifier_delai`, la règle de `noter` et `joker` : futur ou plus ancien → 404 « jour hors fenêtre »), plan existant (404 « aucun plan ce jour ») ; une lecture seulement, jamais listée dans `a_faire` ; `/adviza/cartes` → `{contrat, releve_le, langue, cartes[{id, nom, quete: null | {id, objectif}, notions[{id, titre, etat}]}]}` (`etat` ∈ acquis · en_cours · debloque · verrouille) ; `/adviza/concept/<id>` → `{contrat, releve_le, langue, id, titre, domaine, lecon, version_longue, analogies, anecdotes[{texte, source{reference, titre, lien}}], sources[{reference, titre, lien}], avertissement: null | texte}` (alias admis, `id` = l'id actuel ; `lien` vrai seulement pour une URL que le registre admet, #45 ; avertissement pour le domaine finance, inv. 9 ; 404 « concept inconnu ») ; `/adviza/catalogue` → `{contrat, releve_le, langue, cartes[{id, nom, concepts, quetes[], inscrite, quete_active}]}`. `profil` = résumé autorisé, jamais `brainiacs/<élève>/profil/` (inv. 11) ; `a_faire` = le jour seulement (#103, inv. 15) ; maîtrise = caches du matin, comme la page du QR. `cartes` et `concept` prennent la langue du plan du jour, ou celle de `general.md` si le plan manque ou est illisible. Refus : `{contrat, ok: false, motif}` (401, 403, 404, 405 avec `Allow: GET, POST` pour toute autre méthode, 421, 500 au motif fixe « lecture impossible » ou « erreur interne », détail au journal seulement). Schéma `Bearer` sans tenir compte de la casse.
8. **Actions ADVIZA** (PROF-A3, `freinet/adviza_actions.py`) : `POST /adviza/actions/noter` `{question_id, note, jour?}`, `/joker` `{jour?}`, `/choisir_carte` `{carte_id, quete_id?}` — liste fermée, `repondre` hors contrat v1 (#105, #115). En-tête `Idempotency-Key` obligatoire (`[A-Za-z0-9:._-]{1,128}`). Corps borné avant lecture : `Content-Length` obligatoire (411 sans lui ou avec `Transfer-Encoding`), JSON ≤ 4 Kio (`CORPS_MAX`, 413), `Content-Type: application/json` (415), JSON invalide 400. Réponse `{contrat, ok, motif?, effet?}` (`contrat` ajouté à l'envoi, jamais stocké) : 200, 422 (refus métier, ex. ticket trop ancien), 409 (clé reprise pour une autre requête), 400, 404 (`action inconnue : <nom>`), 408 (corps qui n'arrive pas), 411, 413, 415, 503 avec `Retry-After: 1` (conflit passager `EnvoiConcurrent` : « trop d'envois simultanés : réessayer »), 500 (motif fixe « action non enregistrée », « action peut-être appliquée : réessayer » si l'action a pu s'appliquer sans que sa réponse soit enregistrée, ou « erreur interne » ; détail au journal seulement). Une clé = une exécution par élève : clé et réponse en ajout seul dans `adviza_requete` (migration 004), rejeu identique avec `Idempotent-Replayed: true` ; empreinte canonique (ordre des clés JSON indifférent, `null` = absent) ; une requête invalide, un conflit passager ou une panne laisse la clé libre (le rejeu est sûr : le domaine est idempotent en dessous). Une API par racine (son port est lié) : un verrou de processus (`verrou_actions`) entoure vérifier, agir et enregistrer ; si la clé est malgré tout prise entre-temps, la réponse enregistrée fait foi et est rejouée. `noter` et `joker` sont ceux du QR (canal `adviza`, même `revue_id` que le QR) ; `choisir_carte` = inscription à une carte publiée (`eleves.valider_inscription`).

- L'espace d'un ticket prend la langue de son plan (`langue:`) : libellés (`freinet/libelles_espace.py`) et bibliothèque (`bibliotheque/en/`) ; les pages ouvertes (`/cours`, `/fiche`, `/c`) restent en français (PROF-12).

## Outputs
- lignes `revue` dans `data/freinet.db` ; `plan_du_jour.statut` = `note` (et `joker`) ; `inscription` (action `choisir_carte`) ; `adviza_requete` (clés d'idempotence, ajout seul)

## Human check
Aucune : l'élève note lui-même ; l'honnêteté est tenue par la règle du transfert (inv. 5).
